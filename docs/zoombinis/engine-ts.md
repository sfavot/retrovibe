# Moteur TypeScript de Zoombinis (tâche F3)

Cœur du moteur, sans écran (les écrans arrivent en vague G). Comportement d'origine : `engine.md` (§1 démarrage, §2 écrans, §7 entrées, §8 hasard) ; plan : `plan.md`, « Vague F ». Le cadre est **commun** aux jeux Mohawk et décrit dans `docs/mathemagique/engine-ts.md` ; ce document ne dit que ce que Zoombinis y ajoute.

## Carte du code

### Commun (`src/engine/mohawk/`, `src/ui/mohawk/`)

`Engine<Id, Ext, Cursor>` (ordre d'un tick, présentation, curseur, pause), `SceneManager` (changement d'écran différé), `Clock` (tick de 17 ms), `Input`, `MsvcRandom` (le générateur de `1080:0028`, `engine.md` §8), `Resources` / `Archive` (`memo`, `tbmp`, `tbmpImages`, `shpl`, `strl`, `\0SND`), `graphics/`, `audio/`. Zoombinis n'y change rien.

## Ce que les vagues suivantes branchent

- **Vague G, écrans** : une `SceneFactory` par écran, enregistrée avec `engine.register(ScreenId.x, …)`. `load` ouvre l'archive de l'écran (`ctx.resources.open`), `enter` crée les objets, `tick` remplace le Tick `+0x08`, `key` le handler `+0x10`. La transition `XFER` (écran 2) est un écran comme les autres, demandé par la règle de `engine.md` §2.2.
- **Features `SCRB` / `SCRS`** (`engine.md` §3.5) : `engine/features.ts`, voir « Features » ci-dessous.
- **Régions `REGS`** : `regs` donne les mots bruts ; `data/regs.ts` fournit les ancres (`parseAnchors`, `anchorPosition`).
- **Curseurs** : l'hôte navigateur fabriquera les curseurs CSS depuis `curs(archive, 1…5)` + `cursorToRgba` ; `setCursor("curs1")`…
- **Son** : service de F4, branché dans le contexte comme un service.
- **Raccourcis** (`engine.md` §7.2) : `Engine.addKeyHandler("after", …)` ; `Ctrl+V`, `Ctrl+Y`, `Ctrl+T`, `Ctrl+J`, `Ctrl+U`, `Ctrl+H` basculent `ctx.prefs`. `Ctrl+Q` (et `Ctrl+N`, `Ctrl+C`, `Ctrl+S`) passent par la boîte d'enregistrement, donc le moteur ne quitte pas de lui-même.
- **Persistance** des préférences et des parties (`.WHO`, `HostStorage`) : pas encore, vague G.

## Son

`src/games/zoombinis/engine/sound.ts` : `ZoombinisSound` (clé `ZOOMBINIS_SOUND`), construit avec l'`AudioSink`, `ZOOMBINI.MHK` et `MIDIMPC.MHK`, et le `SYSX` de `MIDIMAP.DAT` (64 messages envoyés avant chaque musique). Le moteur appelle `tick()` à chaque tick, **en dernier** (crochet posé à la fin de `installServices`, après les features, la partie et la boîte de dialogue), comme `11a8:04b9` qui traite la file (`11a8:2d3f`) après la lecture des features : un son posé sur une image de script (voix des trolls de la hutte, des gardiens…) part dans le tick où l'image s'affiche. Avant, il partait au tick suivant (17 ms de retard sur l'image). Le reste du décalage perçu vient de la sortie audio de l'appareil (latence Web Audio, casque Bluetooth), hors du moteur.

- `queue(id)` (`11a0:0ee7`) : file effets / voix de 32 places (ids < 30000) et file musique de 32 places (ids ≥ 30000 et 0) ; file pleine : l'id est perdu. `tick()` (`11a8:2d3f`) vide la file musique dans l'ordre d'arrivée et applique à la file des effets la priorité de `11a8:317c` (voir plus bas) ; routage : < 1000 → `ZOOMBINI.MHK`, 1000…19999 → archive de l'écran (`setScreenArchive`), 20000…29999 → `ZOOMBINI.MHK` (« s-sound », joué normalement ; flux probable dans l'original), ≥ 30000 → `tMID` de `MIDIMPC.MHK`. Id absent : ignoré.
- `queue(0)` rejoue la dernière musique (`DS:3ea6`). `musicEnabled` (`DS:a43b`) / `effectsEnabled` (`DS:a43a`) : coupé, `queue` ignore le genre ; couper la musique l'arrête ; la rallumer ne rejoue rien (**hypothèse**).
- **Un seul effet à la fois** (`engine.md` §6.2, `DS:0296` = 1 canal) : démarrer un son coupe celui qui joue. À chaque tick, parmi le son en cours et les ids en file, seul le plus prioritaire est gardé (le plus récent à égalité), les autres sont perdus. `priorityOf(id)` = `32 − i` pour la première plage `i` de la table de l'écran, 0 hors plage ; la table (`SCREEN_SOUND_PRIORITIES`, relevée dans l'Enter de chaque écran) est posée par `setScreenArchive` d'après le nom de l'archive, remise à [996…997] par `setScreenArchive(null)`. `currentEffect` = `DS:a402` (dernier id démarré). Écart : les écrans cachés 19 / 20, qui lisent `PICKER.MHK`, prennent la table du choix.
- WAVE de répétition `0xffff` : joué en boucle jusqu'au son suivant (les pas et roulettes relancés toutes les deux images par les scripts de marche ne s'empilent plus : c'était le défaut « le bruit des roulettes ne s'arrête plus » des gorges, jusqu'à 54 boucles superposées pour deux traversées) ; une musique à la fois, bouclée par les repères du séquenceur (**hypothèse**).
- `soundIdForSnoid(code, voiceType, variant, rng)` : id d'un son de `SCRS` dépendant du Zoombini (`engine.md` §3.7, **probable**).

## Features (tâche G2)

`engine/features.ts` : port de `11a0:033a` (interpréteur), `11a8:0ad6` (création), `11a8:1be6` (changement de script), `11a8:216f` (accès aléatoire), `11a8:14ab` / `15a6` / `166e` (plages et résolution id → groupe) et `11a0:0000` (groupes de formes). Service `FEATURES` (`Features`), installé par `installFeatures(engine)` après `installServices` : crochet de tick qui joue les features échues (`tick ≥ next`) avant le `tick` de la scène, puis recompose **l'écran entier** (fond, features par profondeur croissante) et demande la présentation si l'une a joué. Pas de rectangles sales.

- Une scène, dans `enter` : `setArchive(archive)`, `setBackground(surface)` (le fond : tout ce qui n'est pas dans une feature doit y être, l'écran est recopié depuis lui), `defineGroup(k, tbmpId, withAnchors)` (k de 0 à 7 ; `setGroup(k, createSheet(...))` pour une planche déjà construite), `setScripts(premier, nombre)` / `addScripts(premier, nombre)` (le groupe d'un id de script est le rang de sa plage), puis `create({ delay, script, flags, depth, position, onEvent, onImage, onBeforeDraw, onAfterDraw, notifyEnd, source })`. Dans `leave` : `clear()` (features, groupes, plages, fond).
- `FeatureFlag` : interprétés `firstImage`, `noDraw`, `active`, `resetOnce`, `stopEachImage`, `queueScript`, `noReplay`, `stopAtEnd`, `relative`, `staticFirst`, `random` ; stockés sans effet (non interprétés) `snoid`, `other`, `flag4000000`, `region`. Aléatoire : `ctx.rng.range(0, dernière)` (`10a8:04e8`). Sons des terminateurs : `ZOOMBINIS_SOUND.queue(id)` (donc coupés si les effets le sont).
- Rappels : `onEvent(image, n, feature)` (`n` = octet bas du terminateur − 1, `FEATURE_END` = `0xffff` à la fin ; vidé après la fin, comme `+0x10`), `onImage(feature, parts)` (reçoit les parties de l'image avant la soustraction de `REGS` et renvoie celles à utiliser ; une partie peut porter sa propre `sheet`, avec ses ancres : planche d'une autre archive ou d'un autre groupe, pour les Zoombinis), `onBeforeDraw` / `onAfterDraw(feature, screen)`. `source(id)` remplace les plages (`SCRS`).
- Écarts assumés : `depth` numérique au lieu de l'insertion relative à une autre feature ; `notifyEnd` vrai par défaut (l'original exige `+0x2f`) ; groupes de synchronisation (`+0xde`), région `0x8000000` et écrêtage `+0xe2` non portés ; `seek(feature, n)` règle l'image à `n − 1` pour que l'échéance suivante lise `n`.
- Images de 24 cases (FERRY, LILLY) : la boucle ne lit pas leur terminateur, relu comme image sans case ; celle-ci laisse le tampon et l'écran inchangés, mais son rappel d'événement et son son partent. Détail dans l'en-tête du fichier. Une case vide (`w = 0`) termine aussi la liste de parties (le tampon est lu jusqu'au premier `w = 0`).
- Tests : `test/zoombinis/features.test.ts` (scripts synthétiques et `BASECAMP`). L'écran de démonstration `scenes/demo.ts` (F à G) a été retiré en fin de vague H.

## Texte (tâche G3)

**Ce que fait le jeu.** `1018:04a0` crée deux polices TrueType **CornerStone** (`CORNER.TTF`) selon la langue (`DS:5cfc`) ; en français (valeur 1) : `LOGFONT` de hauteur 13 (`DS:9638`) et 16 (`DS:963c`), par `11b8:1158` puis `CreateFontIndirect` (`11e8:0ee9`). Celle-ci passe `lfHeight = -hauteur` (hauteur de caractère), graisse 400, ni italique ni souligné, charset par défaut, qualité par défaut (GDI sur écran 256 couleurs : pas de lissage). Le texte est écrit par `11e8:5d70` : `DrawText` avec `DT_WORDBREAK | DT_NOCLIP | DT_EXTERNALLEADING | DT_NOPREFIX` (0xb10) plus `DT_CENTER` (drapeau 2) ou `DT_RIGHT` (drapeau 4) ; centrage vertical (0x20) et bas (0x40) calculés à la main sur la hauteur mesurée (`DT_CALCRECT`) : haut = milieu du rectangle − moitié de la hauteur, ou bord bas − hauteur ; découpe par un rectangle distinct (`param_5`, `IntersectClipRect`). Fond transparent (`SetBkMode(1)`) dans le chemin par bitmap hors écran ; la couleur de texte est celle du contexte (`SetTextColor` dans `11e8:1067`, à partir du stylo), ici un indice de palette. Les chaînes viennent des `STRL` de `TEXTSTR.MHK` (`1178:0103`) ; `FUN_1010:0000(index, liste)` renvoie la chaîne *index − 1* (index 1-based, 0 ou trop grand = nul).

**Ce que fait le port.**
- `MohawkHost.text?: HostText` (`engine/mohawk/host.ts`, facultatif ; Mathémagique n'en a pas) : `metrics`, `measure`, `rasterize` synchrones ; une police est `{ famille, hauteur LOGFONT }`.
- `ui/mohawk/font-raster.ts` : `loadFontFace` (`FontFace` depuis les octets du `.ttf`) et `CanvasText` : chaîne dessinée en noir sur un canvas 2D transparent, seuil d'alpha à 128 → masque 0/1. Hauteur `LOGFONT` → taille CSS suivant la règle GDI : négative = taille em, positive = hauteur de cellule (mise à l'échelle d'après `fontBoundingBox*`), 0 = 12 px.
- `engine/text.ts` : `FONTS.small` (−13) et `FONTS.large` (−16) ; `ZoombinisText.drawText(surface, police, texte, rect, drapeaux, indice, clip?)` (`TextFlags` : `center`, `right`, `vcenter`, `bottom`), `layout` (= `DT_CALCRECT`), `measure`, `lineHeight` ; `TextStrings` (`list(id)`, `get(id, index 1-based)`, `ids`) sur `TEXTSTR.MHK` (portée `persistent`, `STRL` décodées une fois en Mac Roman) ; service `ZOOMBINIS_TEXT` posé par `await installText(engine)` (après `installServices`).
- `ui/browser-host.ts` : `ZoombinisBrowserHost` (hôte commun + `text`), `await loadText(host)` charge `CORNER.TTF` par `host.loadFile` avant le démarrage.
- Tests : `TestHost.text` = police factice à chasse fixe (`round(0,6 × h)` de large, cellule pleine) ; `test/zoombinis/text.test.ts`.

**Écarts.** Le canvas du navigateur lisse puis on seuille : contours proches mais pas identiques à GDI (hinting, graisse). Largeurs arrondies à l'entier, métriques `hhea` au lieu de `winAscent` / `winDescent` (écart possible d'un pixel). Pas d'interligne externe (`DT_EXTERNALLEADING` sans effet) ni d'expansion des tabulations. Fond toujours transparent (le chemin direct de l'original utilise le mode du contexte, non relevé). Pas de crénage (GDI n'en applique pas par défaut). Un mot plus large que la ligne est coupé entre deux caractères.

Constats de lecture du code (à la place de `screens.md` quand ils diffèrent) :

- `S+0x54` est effacé **seulement** quand des perdus sont rendus ; il est levé à l'entrée de 7, 10, 13, 16 et reste levé après une étape parfaite. Le monument et la marque « sans perte » exigent ce drapeau, pas la dernière épreuve ; seule la dernière épreuve pose le monument et monte le niveau.
- La marque de réussite d'`1168:36e1` utilise le niveau de l'étape (`S+0xC2`), même en entraînement ; `1108:0000` utilise `1168:515d` (niveau d'entraînement compris, moins 1 après une montée de niveau).
- Les réserves de groupe `S+0xA462` / `S+0xA6C8` / `S+0xA1FC` contiennent le groupe **parti** du camp (drapeau `flagA` à 1) ; au retour de perdus elles sont purgées de leurs membres présents puis reçoivent les perdus. À l'arrivée au camp, le tampon est remplacé par cette réserve (les perdus, ou le groupe laissé en retournant à la carte) et ses survivants sont versés au présentoir (`10b0:1ac9`) si le drapeau n'est pas levé. Retour à la carte depuis un camp : le groupe est gardé (aucune perte, `S+0x4A` inchangé) ; depuis une épreuve, la carte abandonne le groupe (`1110:03b8`).
- Une entrée de 22 octets est : attributs (4), rectangle de l'emplacement (8, lu par `10b0:1217`), état (10) ; l'identifiant de la fiche n'est pas recopié dans les réserves.
- La date d'un monument : année en mot (`S+0x62`), mois (`S+0x82`), jour (`S+0x92`) d'après `10a8:0c75` ; le tirage « au hasard » fait 63 essais puis le balayage.
- Fin de jeu : `S+0x4E > 0x270` ; objets décoratifs de la ville 0x14 à l'arrivée, 0x28 quand la phrase finale se lance (`1188:0ce5`).

Hypothèses et points ouverts : rappel de `1168:515d` hors épreuve (table `DS:5206`, non extraite) ; `S+0x20` initial (`[908a]`) ; valeur par défaut de l'emplacement (`DS:072e`), lignes du présentoir (`[6ddc]` supposé 125) ; mapping des messages `STRL` 1020 à 1026 ; sens de `flagB` (`S−0x56CE`) ; reprise d'une partie enregistrée **dans** un camp (`11a0:141e` : les camps rangent leur groupe par `Dialogs.addBeforeSave`).

## Zoombinis à l'écran (tâche G-b0)

`scenes/snoid.ts` : aide commune des écrans (choix, transitions, camps, ville) pour afficher un Zoombini animé, lui faire jouer un `SCRS` et le faire marcher sur `NODE` / `PATH`. Tests : `test/zoombinis/snoid.test.ts` et `demo.test.ts`.

- `snoidAssets(ctx)` (mémoïsé par archive) : planches 3000 / 3100 / 3200 de `ZOOMBINI.MHK` (archive `persistent`, déjà ouverte par `installServices`) avec leurs `REGS` propres (`SNOID_REGS_IDS` : 100 / 101, 102 / 103, 3200 / 3201, que `createSheet` ne sait pas dériver de l'id de la planche) et `script(id)` pour les `SCRS` communs 100 à 150. `screenScripts(archive)` donne une source de `SCRS` pour ceux d'un écran (rejet, « normaux »).
- `createSnoid(ctx, zoombini, options)` → `Snoid`, dans `enter` après `openScreen`. `zoombini` : une fiche `Zoombini` de la partie ou des `ZoombiniTraits`. Options : `position` (pieds), `facing`, `small`, `depth` (défaut 1, fixée à la création), `delay` (défaut 6), `idleVariant`, `scripts`, `onArrive`, `onEnd`, `onEvent`. Le Zoombini est une feature (`FeatureFlag.snoid`) : `closeScreen` / `features.clear()` le détruit, `destroy()` le retire seul.
- Composition : le crochet `onImage` de la feature appelle `composeSnoidCells` sur `image.cells` **complètes** (l'emplacement est le rang de la case) et rend des parties `{ w: image de la planche, x, y, sheet }` ; `Features` retranche les `REGS` de la planche de chaque partie (la composition n'en retranche donc pas elle-même).
- Scripts : `play(id, flags = 0, { kind, at })` (`flags` = `FeatureFlag`, 0 = en boucle, `stopAtEnd` puis `onEnd`, `stopEachImage` = première image seule) ; ids 100 à 150 = famille `base` (position = celle du Zoombini), autres ids = script d'écran `normal` (ou `reject`, planche 3100) posé par `scriptAnchorOffset` (finit sur `at`, ou démarre à la position courante). `idle()` = `100 + idleVariant`, image arrêtée. `face(0 | 1)`, `setSmall`, `moveTo` rejouent le script courant.
- Voix : les terminateurs `0xc9…0xda` sont traduits par `snoidVoiceIdForEvent` (hasard : `ctx.rng.range`) et mis en file dans `ZOOMBINIS_SOUND` ; les autres évènements vont à `onEvent(n, snoid)`.
- Marche : `walkTo(destination, map?)` (`startWalk` / `tickWalk` ; `map` = `{ nodes, paths }`, sans carte : ligne droite) et `followPath(nodes, path)` (jusqu'au dernier nœud de `path`). **Pas de tick à brancher** : la marche est cadencée par la feature, un pas à chaque image du script de marche, soit toutes les `delay` = 6 ticks (§4.2), dans le crochet `onImage` ; le premier pas a lieu à la première lecture d'image qui suit `walkTo`. Quand le secteur change, le script `100 + 5 × pieds + secteur` est rechargé sans décaler l'échéance ; à l'arrivée : pose d'attente puis `onArrive`. Rien dans `services.ts`.
- `features.ts` : `finish` retire désormais `onEvent` **avant** de l'appeler avec `FEATURE_END` (même comportement observable, mais le rappel peut installer le script suivant sans être effacé : `onEnd` peut relancer `play`).
- Démo : après le décor de `BASECAMP`, cinq Zoombinis variés entrent un à un (14 ticks d'écart) à gauche du nœud 1, suivent le chemin 1 de `PATH` 1000 (nœuds 1, 2, 7) et s'arrêtent à la file, de 34 pixels en 34, en pose d'attente.
- Limites : une image dont la première case est vide n'appelle pas `onImage` (reproduit `Features`) ; l'animation d'attente (états 0 / 6 : clignements, `130…145`) et la marche d'un Zoombini vers un autre (états 5, 10) ne sont pas portées ici.

## Logo et carte (tâche G6)

`src/games/zoombinis/scenes/{logo,map}.ts`, testés dans `test/zoombinis/{logo,map}.test.ts`. Les scènes ne sont pas enregistrées dans `scenes/index.ts` (l'assemblage est fait à part) ; les tests les enregistrent eux-mêmes.

## Dialogues et raccourcis (tâche G5)

`engine/dialog.ts` (service `DIALOG`, `installDialog`, `confirmLeaveToMap`), `engine/shortcuts.ts` (`SHORTCUTS`, `installShortcuts`) ; tests `test/zoombinis/{dialog,shortcuts}.test.ts` (aide : `dialog-test-env.ts`, écran factice sur l'écran 1). Étude de l'original : `screens.md` §1.4 et §5.2.

**Branchement.** Dans `installServices`, à la fin (après `installGame`) : `await installDialog(engine); installShortcuts(engine);`. `installDialog` ouvre `ZOOMBINI.MHK` (déjà gardé) et ajoute un crochet de tick **après** ceux des features et du jeu (ordre d'installation) ainsi qu'un gestionnaire de touches `before` ; `installShortcuts` ajoute le gestionnaire `after`. Les deux sont sans effet s'ils sont déjà installés. Le menu de la carte (`openMainMenu`) appelle `ctx.services.get(DIALOG).openMenu(ctx)`.

**Saisie du nom.** La boîte d'enregistrement (mode 3) lit aussi le champ HTML invisible commun (`Host.textInput`, un `TextInputPort` de `src/engine/mohawk/text-input.ts`, implémenté par `src/ui/mohawk/text-input.ts`) : il prend le focus à l'ouverture (clavier virtuel, accents composés), son texte passe par `canTypeChar` et la limite de 18, `\b` efface, `\n` valide, et le focus revient au canvas à la fermeture ; les touches simples gardent `handleKey` (le champ ne relaie que ce qui n'en vient pas).

**Principe.** Une pile de couches (menu, chargement, enregistrement, oui / non, crédits, « à propos »). Tant qu'il y en a une : le gestionnaire `before` prend toutes les touches ; à chaque tick le crochet traite les clics du tick puis les **vide** (`input.flush`, la scène du tick ne les voit pas), déclenche les boutons arrivés à échéance (2 ticks après le clic), recompose l'écran (`features.compose()` : fond puis features) et dessine les couches par-dessus. L'écran dessous continue donc de jouer, comme l'original. À l'ouverture l'image de l'écran est enregistrée, à la fermeture elle est restituée puis les features sont invalidées (couvre aussi un écran qui dessine hors des features). Si l'écran change sous la boîte (`scenes.currentId`), elle est abandonnée. Pas de modification de `features.ts` : le dessin par-dessus est celui du crochet de tick.

**API.** `Dialogs` (`ctx.services.get(DIALOG)`) : `openMenu(ctx)`, `openLoad`, `openSave`, `openCredits`, `openAbout`, `open(ctx, 1 | 2 | 3 | 5)`, `confirm(ctx, { message, yes, no?, onYes?, onNo?, mode? })` (modes 4 et 6 ; sans `no` : bouton unique), `confirmLeaveToMap(ctx, onConfirm, onCancel?)` (aussi exportée en `confirmLeaveToMap(ctx, …)`), `newGame`, `quit`, `startNewGame`, `toggleOption(ctx, option)`, `showMessage(ctx, indice 1-based de STRL 2023, type)`, `closeTop`, `closeAll`, `addBeforeSave(hook)` (à appeler avant chaque écriture depuis la boîte : rôle de `11a0:141e`, qui range le groupe courant dans la réserve de l'écran), `isOpen`, `modes`, `prompt`, `message`, `isDirty()`.

Chargement : `SaveStore.load`, `session.name`, `resumeScreen`, `goTo`. **« Partie modifiée ».** L'original lit `[87e4]` (posé par les écrans). Ici l'état est comparé à la dernière partie écrite (`serializeGame` du fichier de la partie nommée, ou de l'état au dernier chargement / nouvelle partie / enregistrement pour une partie anonyme) : aucun crochet n'est demandé aux écrans.

**Options.** `toggleOption` bascule `game.options`, met à jour `ctx.prefs` et le son sans attendre le tick suivant (la musique rallumée rappelle la dernière, `queue(0)`). Les raccourcis (`shortcuts.ts`) en affichent le message de `STRL` 2023 (plaque `tBMP` 3001 au bas de l'écran, 90 ticks, une seule à la fois, rien tant qu'une boîte est ouverte). `Ctrl+V` / `Ctrl+B` = musique, `Ctrl+Y` = voix et effets (le code, pas les libellés du menu). **Curseur** : aucun type de curseur « caché » n'est ajouté ; `[a43d]` ne masque le pointeur que pendant le transport d'une pièce (`screens.md` §5.2) : `Ctrl+H` bascule l'option (`hideCursorWhileCarrying`, sens de `[a43d]`) et affiche son message, à charge pour les écrans de transport de lire `ctx.prefs`. **Souris aimantée** et auto-aimantation : bascule et message, sans effet.

## Kit des épreuves (tâche H0)

Une épreuve donne ses **places** (pieds), ses **cibles** de dépôt, un rappel de **décision**, sa voix d'introduction et ses boutons ; le kit gère le reste. ## Tactile (vague J)

**Chemin d'un doigt.** `ui/pointer.ts` (`bindCanvasPointer`, commun) convertit chaque doigt en `pointerdown` / `pointermove` / `pointerup` vers `Input` (`mouseDown`, `moveMouse`, `mouseUp`, bouton gauche) par `ui/mohawk/browser-host.ts` ; Zoombinis n'utilise pas le mode `tap` ni de barre tactile. Toucher = appui et relâchement dans le même tick (les écrans lisent `buttonEvents`, y compris les boutons « go », « carte », flèches des camps tenues par `isButtonDown`) ; glisser = appui, déplacements, relâchement ; l'appui long (`onLongPress`) n'est pas utilisé. Le canvas a `touch-action: none` (pas de défilement ni de zoom au doigt). Le champ invisible du nom de partie (`Host.textInput`) prend le focus à l'ouverture de la boîte d'enregistrement : le clavier virtuel monte, « Entrée » valide.

**Correctif : glisser-déposer au doigt** (`Host.pointerIsTouch`, `ui/browser-host.ts`, `engine/game.ts`). L'option « souris aimantée » (vraie par défaut dans une partie neuve) rend le transport « collé » : relâcher ne dépose pas, l'appui suivant dépose. Au doigt, un glisser lâché sur sa cible laissait le Zoombini en l'air sous un doigt déjà levé. L'hôte note le type du dernier appui sur le canvas (`pointerType === "touch"`, écouteur de capture) ; le crochet de tick de `installGame` force alors `ctx.prefs.magneticMouse = false` (la case du menu et l'option enregistrée ne changent pas). Le kit (`puzzle-kit.ts`) et Zoombiniville (`town.ts`) lisent cette préférence à la prise : au doigt, relâcher dépose. Un Zoombini touché sans glisser est reposé aussitôt. À la souris rien ne change. Test : `test/zoombinis/touch.test.ts`.

**Parcours joué au doigt** (Playwright, `hasTouch` + `isMobile`, 390×844 et 844×390, `npm run dev`) : logo, choix (attributs, « au hasard », « ajouter », départ), carte, menu, enregistrement (nom saisi), camp 1 (sortie, glisser vers le présentoir), Zoombiniville, et les 12 épreuves de bout en bout avec le robot de règles (glissers au doigt, touchers pour la pizza, la muraille, le piège de cristal, « go »). Aucun écran n'exige un clic droit, un survol ni une touche autre que ce qui suit.

**Ce qui reste hors de portée du doigt** (touches seules, comme dans l'original) :
